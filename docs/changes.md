## add-gloss (Issue #9, PR #10, 2026-10-13)

設計対話で PO が決めたこと: 記号は `^ ` で対象の行のすぐ次に書く。大きさは本文の 60% を整数の pt に丸める。行数の上限は 2 行（対象の上限が 1 行なら 1 行）。色は `#767676`（白とのコントラスト比 4.54:1、3 案から PO が選んだ）。色・大きさ・位置は生成器が決め、原稿からは指定できない。

### 2026-10-13 表の添え訳は行ごとの添え訳の行で書く
- Ruling: 表の見出し行か本文の行のすぐ次の `^ | a | b |` を、その行の各セルの添え訳とする。空のセルは添え訳なし。すべて空なら空の添え訳として拒否し、セルの数が列数と違えば拒否する。
- Reason: 依頼文は「セル内の書き方は設計に任せる」。セルの中に区切りを足す書き方（`Sales ^ 売上`）は `^` を文中に書けなくなり、行も 2 倍に長くなる。行ごとにすれば、ほかの対象と同じ「すぐ次の行」という 1 つの規則で説明できる。
- Cost if wrong: 表の原稿が縦に長くなる。書き手から「書きにくい」と言われたら、別の変更でセル内の書き方を足す。

### 2026-10-13 大きさは比率から計算する
- Ruling: `fit.py` に比率 0.6 と `gloss_pt`（本文の大きさから、四捨五入した整数の pt）を置き、`render.py` と `manuscript.py` の両方が使う。結果は 24・18・14・13・12・11pt。
- Reason: どれも本文の 58〜61% で、依頼の目安 55〜65% に入る。対象ごとに定数を 9 つ置くより、比率 1 つの方が「本文の 60%」という説明と一致する。
- Cost if wrong: 表の 11pt が投影で読みにくい。PowerPoint で投影すれば分かる。比率を変えれば全体が揃って変わる。

### 2026-10-13 配置
- Ruling: 段落の中に置く対象（箇条書き、2 列の項目と文、一言、図の説明文、表のセル、表紙の文）は、対象の段落のすぐ次の段落にし、前の間隔を 0 にする。箇条書きでは `marL` 0.4 インチ・`indent` 0・`buNone`。見出しの添え訳の枠は y 1.225 インチ・高さ 0.375 インチで、添え訳があるときだけ見出しの枠の高さを 0.9 から 0.625 インチにする。表紙のタイトルは、添え訳の高さ g だけ枠を上に上げ、添え訳の枠の下端を 3.8 インチにする。表紙の文に添え訳があれば、その枠の高さを 1.8 から 2.4 インチにする。添え訳のないスライドの図形はいまと同じにする。
- Reason: 見出しの添え訳は 1.6 インチで終わり、本文の枠（1.8 インチから）と重ならない。表紙のタイトル 2 行と添え訳 2 行でも上端は 0.6 インチに収まる。表紙の文 3 行と添え訳 1 行ずつで 2.22 インチ。
- Cost if wrong: 実際の PowerPoint の行の高さが 1.5em と違い、見出しと添え訳が重なるか離れすぎる。PowerPoint で開けば分かる。

### 2026-10-13 高さの判定は、合計が枠を超えうるレイアウトだけに置く
- Ruling: 高さの判定は箇条書き、左右 2 列の箇条書き（新しく足した）、表に置く。表紙・一言・図の説明文・2 列の文には置かず、上限の行数まで書いても枠に収まることをテストで固定する（`test_limits_fit_in_box_height`）。2 列の箇条書きの項目の間隔 10pt は `fit.COLUMN_BULLET_GAP_PT` に移した。
- Reason: 上限の行数で計算すると、一言 3.5 インチ（枠 6.3）、図の説明文 1.75 インチ（枠 2.4）、2 列の文 1.92 インチ（枠 4.9）で、どれも超えない。2 列の箇条書きは、添え訳があると最大 6.25 インチになる。
- Cost if wrong: 上限の値を後で変えたときに、判定のないレイアウトではみ出す。上限を変えると `test_manuscript_fit.py` の上限のテストが赤になり、上限まで書いた原稿のテストを見直すことになる。

### 2026-10-13 後方互換は部品ごとのハッシュで固定する
- Ruling: 変更前のコードで `examples/sample.md` から作った PPTX の部品ごとの SHA-256 を `tests/fixtures/sample_parts.json` に保存し（`docProps/core.xml` を除く）、`tests/test_compat.py` で比べる。
- Reason: 依頼は「今とまったく同じ PPTX」。出力は日時を除いて決定的で、`examples/sample.md` は 6 種のレイアウトをすべて使う。
- Cost if wrong: python-pptx や lxml の版が上がると、添え訳と関係なくハッシュが変わってテストが赤になる。そのときは版の更新の変更の中で、更新前のコードの出力と比べたうえで基準を作り直す（テストのコメントに書いた）。

### 2026-10-13 実装中の判断（タスク 3.1・3.3）
- Ruling: `fit.table_row_height_in` に添え訳の行数と大きさの引数を足し（既定値ではいまと同じ結果）、表の行の高さを `manuscript.py` と `render.py` で同じ関数から求める。`Table.heading_gloss` は見出しの共通の処理と一緒にタスク 3.1 で入れた。
- Reason: 判定と描画は同じ寸法の定義を使う。`heading_gloss` は設計で `Table` にもあると決めてあった。
- Cost if wrong: タスク 3.3 の Files に `fit.py` がなかっただけで、振る舞いは spec のとおり。既定値でいまと同じ結果になることは互換のテストが守る。

### 2026-10-13 表のはみ出しで、超えた行に添え訳がないとき
- Ruling: 下端が最初に枠を超えた行について、それまでのすべての添え訳を除いてもすでに超えるならその表の行を出す。添え訳を除けば収まるのに超えた行に添え訳がないときは、それより上で一番近い添え訳の行を出す。
- Reason: spec は「添え訳を足して初めて超えるならその添え訳の行」とだけ書き、超えた行に添え訳がない場合を書いていない。はみ出しの原因は上の行の添え訳なので、直すべき行を指す方が書き手に役立つ。
- Cost if wrong: 書き手が、指された添え訳とはみ出した行の関係を読み取れない。指す行を変えるか理由の文を直せば足りる。

Handed on: レビューの Minor 指摘と提案 13 件。アーカイブした `tasks.md` の Proposals（`openspec/changes/archive/2026-10-13-add-gloss/tasks.md`）にある。主なものは次のとおり。

## pixel-art-display-size (Issue #6, PR #7, 2026-10-09)

### 2026-10-09 PNG の拡大率の下限を 1 にする
- Ruling: スライドに埋め込む PNG の拡大率を `min(64, max(1, ceil(1024 / n)))` にする（n は長辺のドット数）。n が 64 以下では、add-slide-plugin の「小さな格子の画像は 1024 ピクセルに届かなくてよい」の式と同じ値になる。
- Reason: 格子の上限を外すと、下限 16 の式では 200 ドットで 3200 ピクセル、1000 ドットで 16000 ピクセル四方の PNG になる。長辺 1024 ピクセル以上という目的は、n が 1024 以下なら `ceil(1024 / n)` で満たせる。
- Cost if wrong: 65 ドット以上の格子を PowerPoint が拡大したときに輪郭がにじむ。大きな格子を貼って見れば分かる。

### 2026-10-09 説明文は画像の右端に付いて動く
- Ruling: 図のレイアウトの説明文の左端を、固定位置 `MARGIN_X + IMAGE_MAX + CAPTION_GAP` から、実際の画像の右端 + 0.5 インチに変える。枠の幅 5.2 インチと高さは変えない。
- Reason: 画像が 0.6〜2.4 インチに縮むと、固定位置の説明文は画像から最大 4 インチ離れる。枠の幅を変えないので `fit.py` の判定はそのまま使える。右端は最大 11.2 インチで、本文領域の右端 12.43 インチに収まる。
- Cost if wrong: 説明文の位置がスライドごとに揃わなくなる。図のスライドを並べて見れば分かる。

### 2026-10-09 格子の大きさに上限を設けない
- Ruling: `grid.py` の `MAX_SIZE` と、幅と高さの上限の検査を消し、代わりの上限は設けない。
- Reason: PO の指定。原稿と格子ファイルは利用者が手元で書くもので、外から受け取る入力ではない。
- Cost if wrong: 数千ドット四方の格子では、PNG を作るメモリが数百 MB になる。そうした格子を書く利用者が現れたら、上限を戻す変更を出す。

### 2026-10-09 200×200 の PNG は 1200 ピクセル四方
- Ruling: タスク 2.1 の「1000 ピクセル四方（拡大率 5）」を「1200 ピクセル四方（拡大率 6）」に直し、上の式を正とした。
- Reason: `ceil(1024 / 200)` は 6 で、5 はタスク文の計算の誤り。拡大率 5 では長辺が 1024 ピクセルに届かない。
- Cost if wrong: 200 ドットの格子の PNG が 1 辺 200 ピクセル大きくなるだけで、見た目は変わらない。

Handed on: レビューの Minor 指摘 4 件。アーカイブした `tasks.md` の Proposals（`openspec/changes/archive/2026-10-09-pixel-art-display-size/tasks.md`）にある。
- `tests/test_render.py` の PNG の拡大率のテストのコメントが「16 倍以上 64 倍以下」のまま。
- 左右 2 列の画像のテストが、取った画像が右の列のものかを確かめていない。
- 左右 2 列の画像のテストは 16×16 のアイコンだけ（対応不要の判断）。
- 長辺 1024 ドット以上の格子は拡大しない PNG になる（design のとおり）。

同梱アイコン 14 個は 16×16 のままで、表示は 1.2 インチになる。描き直すかどうかは、受け入れの結果とあわせて別の変更で決める（design.md の合意事項）。

## add-slide-plugin (Issue #3, PR #4, 2026-10-09)

### 2026-10-09 プラグインは `plugin/` に置く
- Ruling: プラグイン本体を `plugin/` に置き、直下の `.claude-plugin/marketplace.json` から `./plugin` を参照する。
- Reason: 直下に置くとハーネスの `.claude/` などが配布物と混ざる。Claude Code と Copilot CLI はどちらも `.claude-plugin/` 形式のマーケットプレイスを読む（このリポジトリが使う agentic-harness が同じ形で両方に入っている）。
- Cost if wrong: Copilot CLI がサブフォルダの source を読めなければ導入できない。タスク 6.2 の実機確認で分かる。

### 2026-10-09 表紙の文の役割を決めない
- Ruling: 表紙の 0〜3 行の文は、副題・名前・日付を区別せずに同じ書式で並べる。文書の作成者のプロパティは空にする。
- Reason: 役割を区別すると原稿の書式が増える。spec は作成者に生成ツールの名前を残さないことだけを求めている。
- Cost if wrong: 作成者欄が空の PPTX を不自然と感じる人がいる。PO の受け入れで分かれば、作成者を原稿で指定する変更を出す。

### 2026-10-09 見出しと文だけのスライドは作れない
- Ruling: `## 見出し` ＋ 1 行の文は 6 種のどれでもないので拒否し、一言か箇条書きを勧める。
- Reason: PO が選んだレイアウトは 6 種で、増やすのは spec の変更になる。
- Cost if wrong: よくある形が書けず、作成役が 1 項目の箇条書きで代用する。点検役の指摘や PO の試用で分かる。

### 2026-10-09 ライセンスは MIT
- Ruling: `LICENSE` は MIT、著作者は joe-yama。
- Reason: 公開するプラグインにはライセンスが要る。PO の agentic-harness と揃える。
- Cost if wrong: 別のライセンスにしたい場合は公開前に差し替える。PR の確認で分かる。

### 2026-10-09 ハーネスの設定は PO が置く
- Ruling: `HARNESS_LINT_CMD`・`HARNESS_LINT_PATTERN`・`HARNESS_TEST_CMD` の値は実装役がスクラッチパッドに書き、`.claude/settings.json` と `.harness/env.json` への配置は PO が行う（タスク 1.3）。
- Reason: `CLAUDE.md` と `AGENTS.md` が、エージェントによるこれらのファイルの変更を禁じている。
- Cost if wrong: 配置されるまで編集ごとの lint と終了前のテストが動かない。CI の job `check` は動くので欠陥は PR で止まる。

### 2026-10-09 小さな格子の画像は 1024 ピクセルに届かなくてよい
- Ruling: 画像の拡大率は式 `min(64, max(16, ceil(1024 / 長辺のドット数)))` のとおりとし、長辺が 15 ドット以下の格子は 1024 ピクセル未満で埋め込む（8 ドットなら 512 ピクセル）。「画像の埋め込み」の文をこの式に合わせて直した。
- Reason: 元の文は「1024 ピクセル以上」と「上限 64」を同時に求めていて、15 ドット以下では両立しない。上限は pixel-art spec の拡大率の範囲（1〜64）と揃っている。にじみは画素が大きいほど目立たず、512 ピクセルでも 1 ドットが 64 画素四方になる。
- Cost if wrong: 小さな格子を大きく表示したときに輪郭がにじむ。PO の受け入れで PowerPoint で見て分かれば、上限を外す変更を出す。

### 2026-10-09 枠の高さも判定する
- Ruling: 行数の上限に加えて、スライドごとに文字の高さの合計を枠の高さと比べ、収まらない原稿を拒否する。高さは「行数 × 文字の大きさ × 1.5 ÷ 72 インチ」（メイリオの行の高さ 1.5em）と項目の間の余白の合計とし、枠の高さと係数 1.5 は `fit.py` の `PT_*` の隣に置いて `render.py` と共有する。表紙の画像の行も拒否する。
- Reason: 最終レビューで、箇条書き 5 項目×2 行と表 7 行×2 行が、どちらも行数の上限内なのに枠とスライドの下端を越えると分かった（PowerPoint で開いて確かめた）。spec「枠からのはみ出しの拒否」は収まらない原稿の拒否を求めており、行数だけでは守れない。上限の数を下げる案より、内容の短い項目を多く書ける余地が残る。
- Cost if wrong: 高さの見積もりが実際より大きいと、収まる原稿まで拒否される。PO の受け入れで見本を開いて分かれば、係数を調整する。

### 2026-10-09 6.2 の実機確認はリポジトリの外で行う
- Ruling: 作成役と点検役の実機確認は、リポジトリの外の作業フォルダで行う。点検役の「5 種のうち 4 種以上」は、仕込んだ 2・3・4・7・12 番だけで数える。Copilot CLI で Agent が見えなければ `.agent.md` への名前の変更を試す（結果は不要だった）。
- Reason: リポジトリの中で動かすと、プラグインの外にある同じ名前のファイルが見つかり、マーケットプレイスから入れた状態を確かめられない（batch E レビュー）。
- Cost if wrong: マーケットプレイスから入れた環境でだけ起きる欠陥を見逃す。PO の受け入れで README の手順で入れて分かる。

Handed on: レビューの Minor 指摘と提案 31 件。アーカイブした `tasks.md` の Proposals（`openspec/changes/archive/2026-10-09-add-slide-plugin/tasks.md`）にある。主なものは次のとおり。
