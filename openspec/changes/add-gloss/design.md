# Design

## Context

動機は proposal.md「Why」、振る舞いは 2 つの delta spec を参照。寸法と文字の大きさは `fit.py` と `render.py` の定数にあり、`manuscript.py` の判定と `render.py` の描画が同じ定数を使う（`tests/test_render.py` の `test_manuscript_and_render_share_size_definitions`）。この変更も、添え訳の大きさと寸法を同じように両方から使う。

## 合意事項（2026-10-13 設計対話、PO 回答）

- 記号は `^ `、対象の行のすぐ次に書く。表はセルごとに `^ | 訳 | 訳 |` の行で書く（PO の依頼文と設計の案を PO が承認）。
- 大きさは本文の 60% を整数の pt に丸める。行数の上限は 2 行、対象の上限が 1 行なら 1 行。
- 色は `#767676`（白とのコントラスト比 4.54:1）。PO が 3 案（`767676`・`808080`・`8C8C8C`）から選んだ。
- 配色・書体・大きさ・位置は生成器が決める。原稿から色や大きさを指定する書式は作らない（PO の依頼文「進め方」）。

## Goals / Non-Goals

**Goals:**

- 英語の本文の各行の下に日本語を添えたスライドを、原稿の 1 行を足すだけで作れる。
- 添え訳のない原稿の出力を 1 バイトも変えない（日時を除く）。

**Non-Goals:**

- 画像の説明（代替テキスト）への添え訳。スライドに文字として出ないので、添えても見えない。
- 自動翻訳、言語の判定。生成器は添え訳の言語を見ない。

## Decisions

### データの持ち方

`manuscript.py` のデータクラスに、添え訳を `str | None`（なければ `None`）として持たせる。いまのフィールドの型と意味は変えず、添え訳のフィールドを既定値つきで足す（既存のテストと `render.py` の読み方を変えないため）。

- `Cover.title_gloss`、`Cover.line_glosses`（`lines` と同じ長さの並び）
- `Statement.gloss`
- `Bullets`・`Figure`・`Table`・`TwoColumn` の `heading_gloss`
- `Bullets.item_glosses`、`BulletsBlock.item_glosses`（`items` と同じ長さの並び）
- `Figure.caption_gloss`、`TextBlock.gloss`
- `Table.header_glosses`（列の数と同じ長さ）、`Table.row_glosses`（`rows` と同じ形）

並びのフィールドは、添え訳がないときも対象と同じ長さで `None` を並べる。添え訳の文字は強調を持たないので `Text` ではなく `str` にする。

### 解析の順序

スライドの行を集めた直後（`_cover` と `_slide` の中で `_check_lines` を呼ぶ前）に、`^` で始まる行を取り除いて、すぐ前の行に結びつける。結びつける先は、原稿の行番号が 1 つ前の行で、かつそれが添え訳でない行のときだけ。それ以外（スライドの先頭、空行の後、添え訳の後）は「対象がない」か「続けて 2 行」として拒否する。添え訳を取り除いた行の並びでレイアウトを判定するので、レイアウトの判定の規則は変わらない。画像の行・`|||`・表の区切り行についた添え訳は、各レイアウトの処理で「対象にできない」として拒否する。

`_check_lines` のインラインの規則（インラインコード、リンク、`__`、`~~`、`*強調*`）は添え訳の本文にも当てる。`**` は添え訳専用の理由（「添え訳の中に強調は書けません」）で拒否し、スライド 1 枚 1 か所の数には数えない。絵文字は行ごとの既存の判定がそのまま当たる。

### 2026-10-13 表の添え訳は行ごとの添え訳の行で書く
- Ruling: 表の見出し行か本文の行のすぐ次の `^ | a | b |` を、その行の各セルの添え訳とする。セルの分け方は表の行と同じ（`_cells`）。空のセルは添え訳なし。すべて空なら空の添え訳として拒否する。セルの数が列数と違えば拒否する。
- Reason: 依頼文は「セル内の書き方は設計に任せる」。セルの中に区切りの記号を足す書き方（例 `Sales ^ 売上`）は、`^` を文中に書けなくなり、行の長さも 2 倍になって読みにくい。行ごとにすれば、ほかの対象と同じ「すぐ次の行」という 1 つの規則で説明できる。
- Cost if wrong: 表の原稿が縦に長くなる。書き手から「書きにくい」と言われたら、別の変更でセル内の書き方を足す。

### 2026-10-13 大きさは比率から計算する
- Ruling: `fit.py` に比率 0.6 と、本文の大きさから添え訳の大きさ（四捨五入した整数の pt）を返す関数を置く。`render.py` と `manuscript.py` は、本文の大きさの定数をこの関数に渡して使う。結果は 24・18・14・13・12・11pt（delta spec「添え訳の見た目」）。
- Reason: どれも本文の 58〜61% で、依頼の目安 55〜65% に入る。対象ごとに定数を 9 つ置くより、比率 1 つの方が「本文の 60%」という説明と一致する。
- Cost if wrong: 表の 11pt が投影で読みにくい。受け入れで PowerPoint を投影して見れば分かる。比率を変えれば全体が揃って変わる。

### 2026-10-13 配置
- Ruling:
  - 段落の中に置く対象（箇条書き、2 列の項目と文、一言、図の説明文、表のセル、表紙の文）: 添え訳は対象の段落のすぐ次の段落で、段落の前の間隔は 0。箇条書きでは `marL` を 0.4 インチ、`indent` を 0 にし、行頭の記号を明示的に消す（`buNone`）。
  - 見出し: 添え訳の枠は、x が本文と同じ、y が `HEAD_TOP` + 見出し 1 行の高さ（0.6 + 0.625 = 1.225 インチ）、高さが添え訳 1 行の高さ（0.375 インチ）。見出しの枠の高さは、添え訳があるときだけ 0.9 から 0.625 インチにする。
  - 表紙のタイトル: 添え訳の行数を n、その高さを g（n 行 × 24pt × 1.5 ÷ 72）とする。タイトルの枠の上端を 1.6 − g、添え訳の枠を 3.8 − g から高さ g で置く。タイトルの枠は下寄せのままなので、タイトルの下端は添え訳の上端に接する。
  - 表紙の文: 添え訳が 1 つでもあれば、表紙の文の枠の高さを 1.8 から 2.4 インチにする。
  - 添え訳のないスライドの図形は、位置・大きさ・順序をいまと同じにする。
- Reason: 見出しの添え訳は 1.6 インチで終わるので、本文の枠（1.8 インチから）と重ならない。表紙のタイトルは、2 行と 2 行の添え訳でも、上端は 0.6 インチで、枠の高さ 2.2 インチに 40pt の 2 行（1.67 インチ）が入る。表紙の文は 3 行と 1 行ずつの添え訳で 2.22 インチになり、2.4 インチに収まる。
- Cost if wrong: 実際の PowerPoint の行の高さが 1.5em と違い、見出しと添え訳が重なるか離れすぎる。受け入れで PowerPoint で開けば分かる。

`render.py` は添え訳の行数を `fit.line_count` で求める（表紙のタイトルの添え訳の枠の高さを決めるため）。

### 2026-10-13 高さの判定は、合計が枠を超えうるレイアウトだけに置く
- Ruling: 高さの判定は、箇条書き、左右 2 列の箇条書き（新しく足す）、表に置く。表紙・一言・図の説明文・2 列の文には置かず、上限の行数まで書いても収まることをテストで固定する。2 列の箇条書きの項目の間の間隔（いま `render.py` の `_block` で 10pt）は、`fit.py` の定数に移して両方から使う。
- Reason: 上限の行数で計算すると、一言は 2.5 + 1.0 = 3.5 インチ（枠 6.3）、図の説明文は 1.25 + 0.5 = 1.75 インチ（枠 2.4）、2 列の文は 1.375 + 0.54 = 1.92 インチ（枠 4.9）、表紙は上の「配置」のとおりで、どれも超えない。2 列の箇条書きは、添え訳がなければ最大 4.09 インチで超えなかったが、添え訳があると最大 6.25 インチになる。
- Cost if wrong: 上限の値を後で変えたときに、判定のないレイアウトではみ出す。上限まで書いた原稿のテストが赤になるので気づける。

### はみ出しの行番号
delta spec「添え訳の行数と枠の高さ」のとおり。箇条書きは、項目の段落と添え訳の段落を上から順に積み、下端が最初に枠を超えた段落の行を出す。表は、行（添え訳の行を含む）の高さを積み、最初に超えた行について、添え訳を除いた高さでもすでに超えるなら表の行、そうでなければ添え訳の行を出す。行数の上限の違反は、いまの `_Parser.fit` に `添え訳` のラベルで渡し、添え訳の行番号で出す。

### 2026-10-13 後方互換は部品ごとのハッシュで固定する
- Ruling: 実装の前に、いまのコードで `examples/sample.md` から作った PPTX の部品ごとの SHA-256 を、テストの基準ファイルとして保存する（`docProps/core.xml` を除く）。テストは同じ原稿から作り直して、部品の名前の集合とハッシュが一致することを確かめる。
- Reason: 依頼は「今とまったく同じ PPTX」。出力は日時を除いて決定的である（2026-10-13 に 2 回作って比べ、違いは `docProps/core.xml` だけだった）。`examples/sample.md` は 6 種のレイアウトをすべて使う（`tests/test_examples.py`）。
- Cost if wrong: python-pptx や lxml の版が上がると、添え訳と関係なくハッシュが変わってテストが赤になる。そのときは版の更新の変更の中で、更新前のコードの出力と比べたうえで基準を作り直す（このことを基準ファイルの横のテストのコメントに書く）。

### 版
プラグインの版を 0.1.0 から 0.2.0 に上げる（原稿の書式が増える機能の追加）。`plugin/.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の両方を変える。

### 2026-10-13 実装中の判断（タスク 3.1・3.3）
- Ruling: `fit.table_row_height_in` に添え訳の行数と大きさの引数（既定値つき、既定値ではいまと同じ結果）を足し、表の行の高さを `manuscript.py` と `render.py` で同じ関数から求める。`Table.heading_gloss` は、見出しを扱う共通の処理と一緒に 3.1 で入れる。
- Reason: 「Context」のとおり、判定と描画は同じ寸法の定義を使う。`heading_gloss` は「データの持ち方」で `Table` にもあると決めてあり、見出しの処理はレイアウトによらず共通である。
- Cost if wrong: 3.3 の Files に `fit.py` がなかったことだけで、振る舞いは spec のとおり。既定値でいまと同じ結果になることは 1.1 のテストが守る。

### 2026-10-13 表のはみ出しで、超えた行に添え訳がないとき
- Ruling: 行を上から積み、下端が最初に枠を超えた行について、それまでのすべての添え訳を除いた高さでもすでに超えるならその表の行を出す。添え訳を除けば収まるのに、超えた行に添え訳がないときは、それより上で一番近い添え訳の行を出す。
- Reason: delta spec「添え訳の行数と枠の高さ」は「添え訳を足して初めて超えるならその添え訳の行」とだけ書き、超えた行に添え訳がない場合を書いていない。はみ出しの原因は上の行の添え訳なので、直すべき添え訳の行を指す方が書き手に役立つ。
- Cost if wrong: 書き手が、指された添え訳とはみ出した行の関係を読み取れない。理由の文に「この行の下端」とあるので、指す行を変えるか文を直せば足りる。
